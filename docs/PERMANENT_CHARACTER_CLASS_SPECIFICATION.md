# Branz MMORPG — Permanent Character Class Specification

Status: Proposed workstream contract  
Owner: Core MMO developer  
Depends on: Player Session, Attributes, Skills, Combat Mastery, Items, and Content

## 1. Product Rule

Every playable character permanently selects exactly one class:

    WARRIOR
    MAGE
    ROGUE

Class selection determines the character's class skills, ultimate, primary
resource behavior, compatible weapon groups, armor policy, and initial attribute
profile. Weapon and mastery choices still create builds inside the class.

Class is stored by stable content ID, for example:

    branz:warrior
    branz:mage
    branz:rogue

Class is permanent for normal gameplay. It cannot be changed through loadout,
equipment, death, respec, reconnect, content reload, or ordinary commands.

## 2. Character Creation and Selection

A new profile enters:

    CLASS_UNSELECTED
      -> CLASS_SELECTION_PENDING
      -> CLASS_SELECTED

Selection requirements:

- The player has an ACTIVE session.
- The class definition exists in the active content snapshot.
- The selection operation has a unique operation ID.
- The player explicitly confirms the class and permanent nature of the choice.
- Starter loadout and skills validate before commit.

Commit atomically stores the class, grants the starter unlocks/loadout, records
an audit entry, and publishes `CharacterClassSelected`.

If starter delivery fails, the selection does not partially commit. Retrying the
same operation returns the original result.

Players without a selected class may use safe menus and class preview content,
but cannot enter normal MMO combat, receive Combat Mastery XP, equip restricted
MMO gear, or accept class-restricted quests.

## 3. Shared Class Structure

Every class definition contains:

    class ID
    display and localization keys
    role weights
    base attribute profile
    primary and secondary resources
    allowed weapon tags
    allowed armor tags
    class skill slot 1
    class skill slot 2
    ultimate skill
    passive tree/root
    starter loadout
    class tags

Class definitions are declarative. They cannot name arbitrary Java classes or
execute unrestricted commands.

## 4. Warrior

Primary identity: durable physical frontline with guard, pressure, and control.

Suggested roles:

    DAMAGE 0.70
    TANK 0.75
    CONTROL 0.45
    SUPPORT 0.15

Resources:

- Stamina for physical skills, guard, and movement
- Rage generated by valid damage dealt, damage received under policy, successful
  guard, interrupt, or encounter contribution

Initial compatible weapons:

- Broadsword
- Greatsword
- Sword and shield

Initial skills:

| Input | Skill | Behavior |
|---|---|---|
| Shift + LMB | Whirlwind | Bounded physical area attack |
| Shift + RMB | Iron Guard | Defensive stance or temporary mitigation |
| Shift + F | Warbreaker | High-impact ultimate with control/pressure |

Warrior passives may improve guard, physical pressure, stagger resistance, and
threat. They cannot create permanent invulnerability or unlimited Rage loops.

## 5. Mage

Primary identity: ranged magic damage, area control, and utility.

Suggested roles:

    DAMAGE 0.80
    CONTROL 0.65
    SUPPORT 0.45
    TANK 0.15

Resources:

- Mana as the primary casting resource
- Optional class-specific charges defined by specialization

Initial compatible weapons:

- Fire Staff
- Arcane Staff
- Wand or focus in a later phase

Initial skills:

| Input | Skill | Behavior |
|---|---|---|
| Shift + LMB | Arcane Burst | Class-scaled magic attack |
| Shift + RMB | Mana Shield | Converts configured incoming damage using Mana |
| Shift + F | Meteor | Delayed area ultimate with server-validated targeting |

Mage passives may improve Mana control, elemental specialization, casting, and
bounded area effects. Mana Shield cannot create negative Mana or bypass damage
transaction ordering.

## 6. Rogue

Primary identity: mobility, precision, combo pressure, and positional attacks.

Suggested roles:

    DAMAGE 0.85
    CONTROL 0.40
    SUPPORT 0.15
    TANK 0.10

Resources:

- Energy with fast bounded regeneration
- Optional combo points generated only by valid authoritative effects

Initial compatible weapons:

- Daggers
- Short sword
- Bow as a later Rogue specialization if enabled

Initial skills:

| Input | Skill | Behavior |
|---|---|---|
| Shift + LMB | Eviscerate | Multi-hit attack with hit deduplication |
| Shift + RMB | Smoke Veil | Defensive/escape utility with explicit visibility rules |
| Shift + F | Shadow Step | Ultimate reposition validated against target and location |

Rogue passives may improve mobility, positional damage, combo efficiency, and
evasion. Teleport and stealth never bypass world protection, safe zones, target
eligibility, or encounter boundaries.

## 7. Class Skill and Weapon Skill Separation

Weapon actions:

    LMB          Basic Attack
    RMB          Weapon Skill 1 / Guard
    F            Weapon Skill 2 / Utility

Permanent class actions:

    Shift + LMB  Class Skill 1
    Shift + RMB  Class Skill 2
    Shift + F    Class Ultimate

Changing a weapon changes weapon actions but not class actions. A class action
may require compatible weapon or armor tags. If the current loadout fails those
requirements, the class skill is disabled with an exact reason.

Class skills are unlocked by class progression or class-owned mastery nodes.
Weapon skills are unlocked by weapon family/type mastery and item/loadout rules.

## 8. Class Progression

Class level and Combat Mastery are distinct:

- Character class level represents broad class progression.
- Weapon family/type mastery represents experience with a combat style.
- Skill proficiency represents optional specialization.

Class XP sources are configured server-confirmed activities such as eligible
combat contribution, encounter completion, and explicit quest rewards. Input
spam and invalid combat effects grant nothing.

Class level cannot decrease on death. Level cap, XP curve, attribute grants, and
skill unlocks are data-driven and bounded.

### 8.1 Class Skill Points

Configured Class Level milestones grant `Class Skill Points`. Initial policy:

- Level 1 grants the starter class kit and zero spendable points.
- Every level from 2 onward grants one Class Skill Point.
- Major milestone levels may grant an additional point if explicitly configured.
- A milestone grant is stored and applied exactly once.
- Combat Mastery Points and Survival Skill Points cannot be spent in the Class
  Skill Tree.

One XP operation may cross multiple levels. It grants every crossed milestone
point atomically with the level change.

### 8.2 Class Skill Tree

Each permanent class owns a directed acyclic tree. A node defines:

    stable node ID
    owning class ID
    branch ID
    maximum rank
    point cost per rank
    required class level
    prerequisite node ranks
    mutually exclusive group if any
    declarative effect

Node categories:

- `ACTIVE_UNLOCK` — unlocks a Class Skill
- `ACTIVE_MODIFIER` — changes an unlocked skill through a bounded variant
- `PASSIVE` — applies an attribute or rule modifier
- `RESOURCE` — changes bounded resource generation, cost, or regeneration
- `ULTIMATE_UNLOCK` — unlocks the Class Ultimate
- `KEYSTONE` — high-level branch-defining sidegrade

An active modifier cannot replace a skill with an arbitrary Java implementation.
It selects a validated effect node, coefficient, targeting, cost, or behavior
variant declared in the same compatible content snapshot.

### 8.3 Purchase flow

The player opens the Class Skill Tree UI and selects a node or rank:

    inspect current immutable tree snapshot
    -> validate class ownership
    -> validate class level
    -> validate prerequisites/exclusion group
    -> validate available Class Skill Points
    -> commit point spend and new rank
    -> rebuild affected class modifiers/skills
    -> publish event and refresh UI

Purchase uses a unique operation ID. It cannot consume a point without granting
the node rank. Double-click, reconnect, UI reopen, or retry cannot purchase the
same rank twice.

### 8.4 Initial Warrior tree

```text
Warrior
├─ Vanguard
│  ├─ Iron Guard
│  ├─ Reinforced Guard (3 ranks)
│  └─ Unbroken [Keystone]
├─ Berserker
│  ├─ Whirlwind
│  ├─ Blood Momentum (3 ranks)
│  └─ Relentless [Keystone]
└─ Warlord
   ├─ Rallying Shout
   ├─ Commanding Presence (3 ranks)
   └─ Warbreaker [Ultimate]
```

- Vanguard emphasizes mitigation, guard, and threat.
- Berserker emphasizes Rage, physical pressure, and risk/reward.
- Warlord emphasizes control, party utility, and battlefield pressure.

### 8.7 Branch policy

The initial release allows investment in multiple branches, but each class may
equip only:

- Two normal Class Active Skills
- One Class Ultimate
- A configured bounded number of active keystones/passives

Mutually exclusive keystones prevent incompatible final mechanics from being
active together. Owning a node and equipping its action are separate states.
Changing equipped class skills is blocked during combat and does not refund
points.

### 8.8 Respec

Class Tree respec does not change the permanent class.

Respec rules:

- Available only in a safe location and outside combat
- Requires configured Coins/item cost and cooldown
- Shows the exact refund and disabled skills before confirmation
- Refunds eligible Class Skill Points in one transaction
- Clears invalid bindings and restores the configured starter actions
- Rebuilds modifiers once using stable source IDs
- Is idempotent and audited

The initial release supports full-tree respec. Partial branch respec is deferred
until dependency and refund behavior has dedicated tests.

### 8.9 Tree revision and migration

Published Class Trees use immutable revisions. Added nodes require no migration.
Renamed nodes require aliases. Removed nodes require an explicit refund,
replacement, or retained-disabled policy.

Changed costs and prerequisites cannot create negative points or silently remove
unlocked ranks. Failed migration leaves the player on the previous revision,
disables new tree purchases, and exposes an admin repair reason.

## 9. Restrictions and Validation

- Warrior-only skills cannot be equipped by Mage or Rogue.
- Mage-only weapons or armor cannot be equipped by another class unless their
  content definition explicitly includes that class.
- Generic consumables, materials, cosmetics, and configured utility items may
  be shared.
- Class restrictions are validated during equip, login, reload, trade, reward,
  mailbox claim, and repair.
- Invalid loadouts fail closed and retain or restore the last valid snapshot.
- PDC/lore labels do not determine class compatibility.

## 10. Persistence and Repair

The player profile adds:

    class_id
    class_selected_at
    class_selection_operation_id
    class_schema_version

Class progression adds:

    class_level
    class_total_xp
    class_unspent_skill_points
    class_tree_revision

Class node ranks use `(player_uuid, class_id, node_id)`.

The database enforces one selected class per character profile. Ordinary APIs
provide no class-change mutation.

An administrative class repair or migration is allowed only for corrupted or
retired content:

    /branz class inspect <player>
    /branz class repair <player> <target-class> <reason> <confirmation>

Repair validates equipment, skills, mastery compatibility, pending rewards, and
quests before commit. It never silently deletes valuable items or progression.
Incompatible assets route to a documented recovery policy.

## 11. Content Reload and Class Retirement

Removing or renaming a released class requires an explicit migration plan.
Renames use stable-ID aliases. A retired class remains readable until all
profiles migrate.

If a class definition, starter loadout, skill, or weapon reference is invalid,
content reload fails and retains the active snapshot.

Existing sessions retain their validated content revision until the subsystem
performs a safe migration. Class migration is idempotent and auditable.

## 12. API and Events

Public immutable values:

- `CharacterClassId`
- `CharacterClassDefinition`
- `CharacterClassSnapshot`
- `CharacterClassSelectionResult`
- `ClassCompatibilityResult`

Events use the shared domain-event envelope:

| Event | Payload |
|---|---|
| CharacterClassSelected | Player, class ID, starter loadout revision |
| CharacterClassLevelChanged | Player, class ID, old/new level, total XP |
| ClassSkillPointsGranted | Player, class ID, source levels, amount, points remaining |
| ClassSkillNodeUnlocked | Player, class ID, node ID, old/new rank, points remaining |
| ClassSkillTreeRespecced | Player, class ID, refunded points, cost, resulting revision |
| CharacterClassMigrationRequired | Player, current class, target revision, reason |
| CharacterClassRepaired | Player, previous/new class, reason, affected assets |

Quest may query class and class level through public API. Quest cannot mutate
class selection after confirmation.

## 13. Acceptance Criteria

- A new character cannot enter normal MMO combat without selecting a class.
- Selection requires confirmation and commits exactly once.
- Retrying a selection operation cannot grant starter items twice.
- Warrior, Mage, and Rogue receive their configured starter loadouts and skills.
- Class Level milestones grant Class Skill Points exactly once.
- Combat Mastery and Survival Skill points cannot buy Class Skill nodes.
- Node purchase validates class, level, prerequisites, exclusions, and points.
- Duplicate purchase operations cannot consume points or grant ranks twice.
- A player may unlock several branches but cannot equip conflicting keystones.
- Full respec refunds eligible points without changing the permanent class.
- Failed tree migration cannot partially refund or replace nodes.
- Weapon swapping changes weapon skills but preserves permanent class skills.
- Cross-class equipment and skills fail with actionable diagnostics.
- Death, logout, reconnect, respec, and loadout change cannot change class.
- Invalid content reload cannot orphan a selected class.
- Admin repair is confirmed, transactional, idempotent, and audited.
- Quest can query class without importing Core implementation.
- Class selection and compatibility rules pass pure Java tests.
- Paper smoke tests cover selection UI, equipment restrictions, and class skills.
